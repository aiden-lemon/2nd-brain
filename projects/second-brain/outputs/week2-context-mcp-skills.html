00

LLM Wiki란 무엇인가

5′
한 줄 사람과 LLM이 같은 마크다운 파일을 읽는 위키다. 사람용 문서와 AI용 색인이 따로 있지 않다.
먼저 용어 하나

vault = 내 컴퓨터의 knowledge 폴더 하나. Obsidian이 열어 보여주는 그 폴더이고, GitHub의 내 private repo와 같은 것이다. 이 자료에서 "vault", "내 위키", "knowledge 폴더"는 모두 같은 것을 가리킨다.

보통 위키는 독자가 사람 한 종류다. 이 vault는 독자가 둘이다.

  • 사람은 Obsidian으로 읽는다 — 그래프 뷰, 백링크, 검색
  • LLM은 파일 도구로 읽는다 — 경로를 따라 열고, 고치고, 새로 쓴다

둘이 읽는 것이 같은 파일이라는 점이 핵심이다. AI용으로 따로 변환한 사본이나 벡터 인덱스가 없다. 그래서 사람이 손으로 고친 내용이 다음 순간 LLM에게 그대로 보이고, LLM이 쓴 문서를 사람이 Obsidian에서 바로 읽는다.

세 계층이 나뉘어 있는 이유

계층담당고쳐도 되나
raw/ 증거 — 원문 그대로. 웹 클리핑, 문서 원본 불변 수정·이름 변경·삭제 전부 금지
wiki/ 해석 — 원문에서 뽑은 개념. 한 개념당 한 파일 계속 고친다 새 근거가 생기면 갱신
INDEX · topics 입구 — 무엇이 있는지의 목록과 주제 묶음 자동 갱신 위키가 바뀌면 따라간다

해석이 틀렸을 때 위키만 고치면 되고 원문은 건드릴 필요가 없다. 증거와 해석을 같은 파일에 섞어 두면 이게 불가능하다 — 한 번 요약해 버린 원문은 되돌릴 수 없다.

LLM이 읽을 수 있게 쓴다는 것

같은 마크다운이라도 LLM이 판단에 쓸 수 있는 형태가 따로 있다. 이 위키는 세 가지 장치를 쓴다.

  • frontmatter — 기계 판독 계층. 문서 맨 위의 type·status·sources. 사람은 눈으로 넘기지만 LLM은 이걸로 판단한다. 예를 들어 status: needs-update가 붙은 문서는 "근거가 약하다"는 신호로 읽힌다.
  • wikilink — 개념 사이의 연결. [[note-slug]]로 이은 링크가 그래프가 된다. 한 개념에서 관련 개념으로 타고 갈 수 있으니, 질문이 문서 하나를 넘어가도 따라갈 길이 있다.
  • 한 개념당 한 파일. 찾는 단위와 읽어 올리는 단위가 일치한다. 개념 열 개가 한 파일에 있으면 하나만 필요할 때도 열 개를 다 올려야 한다.
오늘의 모든 내용이 여기서 나온다

구조가 곧 인터페이스다. 제목이 제목으로, 표가 표로 남아 있어야 LLM이 "이건 절차의 3단계고 이건 기준값 표"라고 읽는다.

글자만 옮겨진 평문 덩어리는 사람도 LLM도 구조를 다시 추측해야 한다. §04에서 문서 변환 경로를 까다롭게 고르는 이유가 이것이다.

위키 계층이 실제로 하는 일

원문을 그냥 모아두는 것과 무엇이 다른지는 질문을 하나 던져 보면 드러난다. 실제 업무 질문은 대개 문서 하나에 답이 없다.

질문 이 설비 점검 주기가 왜 6개월인가
원문만 문서함 검색 → 파일 3개 찾음 → 각각 열어 읽고 → 직접 이어붙여 결론
위키 INDEX 조회 → 개념 문서 1개 → 근거 3건이 링크로 붙어 있음 → 답 + 출처

점검 주기의 근거는 절차서 · 사고 보고서 · 개정 이력에 흩어져 있다. 검색은 세 파일을 찾아주는 데서 멈춘다. 위키 계층은 그 이어붙이기를 미리 해 둔 결과물이고, 그래서 답에 출처가 함께 붙는다.

이 위키의 성질 셋

무엇이어떻게 보장되는가
답을 검증할 수 있다 모든 답변이 근거 위키 문서를 인용한다. 근거가 약한 주장은 needs-update로 표시돼 남는다
원본이 훼손되지 않는다 raw/는 append-only다. AI가 원본을 건드릴 경로 자체가 없다
어디에도 묶이지 않는다 마크다운 파일과 Git뿐이다. 특정 서비스가 문을 닫아도 파일은 남고, 규칙이 모델 중립적이라 다른 AI로도 굴러간다

그래서 오늘 무엇을 하는가

지금까지 여러분이 써 본 입구는 웹 클리핑 하나다. 브라우저에서 본 글은 버튼 한 번으로 들어오는데, 정작 업무 지식이 가장 많이 쌓인 문서함은 연결돼 있지 않다.

오늘 그 입구를 연다. 그런데 한글·워드 파일은 LLM이 바로 읽을 형태가 아니라서, 구조를 살린 채 마크다운으로 바꿔야 한다. 그 작업을 이해하는 데 개념 셋이 필요하다.

§개념이 위키에서 맡는 역할
01컨텍스트LLM이 한 번에 읽을 수 있는 양의 한계. 위키가 커져도 굴러가게 하는 예산 관리
02MCP없던 능력을 붙이는 규격. 한글 파일을 눈으로 읽는 것 같은 일

01

컨텍스트 — 왜 규칙 파일이 짧아야 하는가

8′
한 줄 AI의 작업 기억은 유한하다. 규칙이 그 자리를 잠식하면 정작 내 문서를 읽을 자리가 없다.

컨텍스트는 AI가 이번 작업에서 한 번에 들고 있을 수 있는 작업 기억이다. 책상 크기와 같다. 책상이 유한하니 무엇을 올려둘지가 곧 성능이 된다.

오늘 나머지 전부가 이 위에 서 있다. MCP도 Skill도 결국 "필요할 때만 필요한 만큼 책상에 올린다"는 같은 문제를 푸는 장치다.

내 vault가 매 세션 읽는 것

Claude가 vault 작업을 시작하면 정해진 순서로 문서를 읽는다. 이 목록이 고정 비용이다. 아무 일을 하기 전에 이미 책상을 차지한다.

CLAUDE.md읽는 순서 · vault 위치 판정짧게
VAULT_RULES.md디렉터리·노트 계약 (권위 문서)약 170줄
wiki/VAULT_MEMORY.md현재 상태와 포인터상한 8 KB
wiki/INDEX.md위키 문서 목록 (질의 진입점)목록만

이 중 VAULT_MEMORY.md에만 기계적 상한이 걸려 있다. 매 세션 무조건 로드되는 파일이라, 여기가 부풀면 원문 읽을 자리가 사라진다.

예시 vault 2,707 bytes (33%) 상한 8,192 bytes

단위가 중요하다. 상한은 줄 수가 아니라 바이트다. "200줄 이하"는 예산이 될 수 없다 — 3 KB짜리 한 줄도 200줄 조건을 통과하면서 로드 비용을 다 쓴다. 그래서 규칙에 검증 명령이 함께 박혀 있다.

wc -c wiki/VAULT_MEMORY.md   # 커밋 전에 확인

예산이 지켜지는 방식 셋

  1. 정책 본문을 복사하지 않고 포인터만 둔다.
    메모리 파일은 "이 얘기는 VAULT_RULES.md § Core Rules에 있다"고만 적는다.
  2. 실행 이력은 별도 파일로 빼고 세션 로드에서 제외한다.
    매 실행 서술은 docs/vault-ingest-log.md로 가고, 메모리에는 Last Ingest: 한 줄(최대 200 bytes)만 남는다. 덧붙이지 않고 교체한다.
  3. 살아있는 액션은 최대 5개.
    ## Open Threads는 닫히면 삭제한다.
그래서 하지 않을 것

VAULT_MEMORY.md에 "오늘 이런 작업을 했다"는 기록을 덧붙이지 않는다. 그 파일은 일지가 아니라 현재 상태판이다.

작업 기록은 Claude가 outputs/runs/와 커밋·PR에 알아서 남긴다.

개발자 심화 — progressive disclosure의 3단계

Agent Skills 표준은 같은 예산 문제를 로드 시점 분리로 푼다. 스킬 하나가 통째로 올라오지 않는다.

단계언제무엇이 올라오나비용
Discovery세션 시작모든 스킬의 name + description만~100 tokens
Activation작업이 description과 매치해당 SKILL.md 본문<5,000 권장
Execution실제로 필요할 때scripts/·references/·assets/온디맨드

그래서 SKILL.md는 500줄 이하로 유지하고 상세 레퍼런스는 references/로 분리하는 것이 표준 권고다. 이 vault의 doc2md-ingest/SKILL.md는 289줄로 이 안에 들어온다.

다음으로

예산 안에서 일하려면 필요한 도구만 그때 붙여야 한다. 도구를 붙이는 규격이 MCP다.

02

MCP — 도구를 붙이는 규격

5′
한 줄 AI가 원래 못 하던 일을 할 수 있게 도구를 붙이는 표준 규격이다. 오늘 실습에는 직접 쓰지 않지만, 3주차 클라우드 연동이 전부 이것이다.

MCP(Model Context Protocol)는 AI가 외부 프로그램·데이터에 연결되는 표준 규격이다. 전원 규격이 통일되면 아무 충전기나 꽂히는 것과 같다. 규격을 맞춘 도구는 어느 AI에든 붙는다.

여기서 대개 한 번 헷갈린다. 그럼 Skill과 뭐가 다른가.

MCP = 능력

  • 원래 못 하던 일을 가능하게 만든다
  • 도구가 프로세스로 붙는다 (서버)
  • 예: 한글 파일을 페이지 이미지로 렌더
  • 연결하면 쓸 수 있는 도구가 늘어난다

Skill = 절차

  • 가진 도구로 무엇을 어떤 순서로 할지
  • 마크다운 문서 한 장 (SKILL.md)
  • 예: 게이트 확인 → 변환 → 판정 → 검증
  • 등록하면 판단 기준이 늘어난다

오늘 실습에서 쓰는 문서 변환은 Skill이다. 그 Skill이 손을 쓸 수 없는 문서를 만났을 때 부르는 게 MCP다.

내 vault에 붙는 MCP

서버무엇을 가능하게언제 쓰나회차
hwp-mcp 한글 문서 읽기·마크다운 변환·페이지 렌더 (도구 35종) 텍스트가 거의 없는 이미지 위주 한글 문서를 눈으로 읽어 전사할 때 필요 시
workspace-mcp Google Drive·Sheets·Slides 검색·읽기·편집 구글 드라이브 문서를 그대로 다룰 때 3주차

실무에서 알아둘 점은 하나다. hwp-mcp는 미리 설치하지 않는다. 한컴오피스와 Java는 필요 없다 — 단 Node 18 이상이 깔려 있어야 실행 시점에 자동으로 받아온다. 1주차 스크립트는 Node를 깔지 않으므로 이 경로를 쓰려면 별도 설치가 필요하다.

둘 중 무엇을 쓰나
  • 문서를 여러 건 처리한다 → Skill (오늘 실습 경로)
  • 한 문서를 붙들고 계속 열어보고 고친다 → MCP 직접 연결. 편집·렌더 도구까지 딸려온다
개발자 심화 — 직접 연결과 전송 방식 
claude mcp add hwp-mcp -- npx -y hwp-mcp

stdio 전송이라 별도 포트·인증이 없다. 로컬 프로세스로 뜨고 표준 입출력으로 JSON-RPC를 주고받는다. treesoop/hwp-mcp v0.2.0(MIT)이며, 2026-08-21 검증에서 도구 35종 노출 · .hwp → md 변환 · 표 추출 성공 · python-hwpx로 만든 .hwpx도 읽는 것까지 확인됐다.

다만 MCP 서버를 붙이면 도구 스키마가 컨텍스트를 차지한다. 35종이 항상 올라와 있을 이유는 없으니, 배치 변환에 스킬 경로를 쓰는 것이 §01의 예산 논리와도 맞는다.

다음으로

이제 손은 있다. 그 손으로 무엇을 어떤 순서로 할지가 Skill이다.

03

Skill — 절차를 문서로 넘겨주기

6′
한 줄 Skill은 마크다운 문서 한 장이다. 사람이 읽는 업무 절차서를 LLM도 읽고 그대로 따르게 만든 것이다.

MCP가 능력을 붙였다면, 그 능력으로 무엇을 어떤 순서로 할지는 여전히 정해줘야 한다. 그 절차를 담는 것이 Skill이다.

중요한 것은 형식이다. Skill은 코드가 아니라 사람이 읽을 수 있는 마크다운 문서다. §00에서 본 "사람과 LLM이 같은 파일을 읽는다"가 절차에도 그대로 적용된 것이다 — 업무 절차서를 사람이 읽고, 같은 문서를 LLM이 읽고 실행한다.

Skill이 어떻게 생겼나

Skill은 폴더 하나와 SKILL.md 한 장이다. 맨 위 메타데이터가 언제 쓸지를, 본문이 무엇을 할지를 담는다.

doc2md-ingest/
├── SKILL.md          # 필수: 메타데이터 + 절차
└── scripts/          # 선택: 실행 코드
    ├── d1-extract.py
    └── test-d1-extract.py

호출 방식이 둘이다.

  • 자동 — "이 워드 파일 넣어줘"라고 하면 메타데이터의 설명과 매칭돼 알아서 뜬다
  • 명시 — /doc2md-ingest처럼 직접 부른다
개발자 심화 — frontmatter 제약과 등록 3경로
필드필수제약
name예≤64자, 소문자·숫자·하이픈만. 부모 디렉터리명과 일치해야 함. "claude"·"anthropic" 예약
description예1–1024자. 무엇을 + 언제 쓰는지 + 매칭 키워드. XML 태그 금지
allowed-tools아니오사전 승인 도구 목록 — 실험적, 구현별 지원 상이
등록 경로위치범위
개인~/.claude/skills/<name>/내 머신 전용, 모든 프로젝트
프로젝트.claude/skills/<name>/repo 체크인 → 클론하면 자동으로 붙는다
플러그인skills/ + plugin.json마켓플레이스 설치·버전 관리

이 vault는 두 번째를 쓴다. 진실원은 projects/second-brain/config/skills/에 두고, .claude/skills/<name>에 상대 심링크를 걸어 노출한다. 절대경로 심링크는 기계 종속이라 커밋하지 않는다.

ln -s ../../projects/second-brain/config/skills/doc2md-ingest \
      .claude/skills/doc2md-ingest

# .gitignore — 통짜 ignore는 심링크 추적을 막는다
.claude/*
!.claude/skills/

Windows 주의: symlink 미지원 설정에서는 심링크가 텍스트 파일로 떨어진다. 온보딩 스크립트가 git clone -c core.symlinks=true로 clone하고 깨진 링크를 검사해 Developer Mode 활성 + 재체크아웃을 안내한다.

Agent Skills는 Claude 전용 형식이 아니다. Cursor·Copilot·Codex·Gemini CLI 등 약 40개 제품이 같은 SKILL.md를 지원한다 (2026-08-21 기준, 변동이 빠른 영역이다).

4주차 예고와 이어지는 지점

스킬이 마크다운 문서라는 것은, 업무 절차를 아는 사람이면 새 스킬을 쓸 수 있다는 뜻이다. 프로그래밍이 아니라 절차서 작성에 가깝다. 4주차에 각자 업무에 맞는 스킬을 직접 만든다.

다음으로

워드 문서를 PDF로 출력해서 넣으면 간단할 것 같다. 그런데 그 경로는 헤딩과 표 구조를 버리고 레이아웃만 남긴다.

결과물은 글자는 다 있는데 무엇이 제목이고 무엇이 표인지 알 수 없는 덩어리가 된다. 위키로 정리할 때 쓸 구조가 이미 사라진 상태다.

04

문서 변환 — 구조를 살려서 꺼내기

11′
한 줄 원본 포맷에서 직접 뽑아야 제목과 표가 산다. PDF로 우회하면 구조가 먼저 죽는다.

내 파일이 어느 경로로 가는가

확장자에 따라 담당 스킬과 변환 경로가 정해진다. 외울 필요는 없다. 스크립트가 확장자와 컴퓨터 환경을 보고 스스로 고른다.

담당 스킬 — .doc/.docx는 doc2md-ingest · .hwp/.hwpx는 hwp2md-ingest · .pdf는 pdf2md-ingest

기억할 것은 하나다. 결과 보고에 D2b가 찍혀 있으면 주의해서 본다.

D2b의 알려진 손실 (실측)
  • 제목이 사라진다 — # 1. 점검 주기가 평범한 문장으로 떨어진다
  • 목록이 평문화된다 — 불릿이 그냥 텍스트가 된다
  • 표 헤더가 한 줄 밀린다 — 다음 단계로 넘기기 전에 표 첫 줄을 눈으로 확인한다
  • 문서에 박힌 이미지가 전부 없어진다 — 복구 불가

내용 자체는 보존된다. 한글 본문, 표 셀 값, ℃·± 같은 단위 기호, 설비코드가 그대로 남는다. 이미지나 제목 구조가 중요한 문서라면 LibreOffice를 설치하고 D2a로 다시 변환한다 — 다만 D2a도 아직 미검증이라 결과를 눈으로 함께 확인해야 한다.

변환 전에 통과해야 하는 게이트 3개

스킬은 변환을 시작하기 전에 세 가지를 확인한다. 하나라도 걸리면 파일을 하나도 쓰지 않고 멈춘다.

#확인걸리면
1 이 문서를 vault에 커밋해도 되는가 고객사·개인 문서면 정식 잉게스트를 중단한다. 변환만 필요하면 vault 밖 변환 모드를 제안한다 — 기본값이 아니라, 내가 명시적으로 선택해야 진입한다
2 어느 vault에 넣는지 확실한가 확실하지 않으면 나에게 묻는다. 아무 폴더로 조용히 넘어가지 않는다
3 같은 파일이 이미 raw/에 있는가 있으면 중단한다. raw/는 덮어쓰기 금지 구역이다
게이트 1이 오늘 가장 중요하다

업무 문서에는 연락처·이메일·사업자번호·상세 주소가 섞여 있다. 내 private repo라도 한 번 커밋되면 지워도 git 이력에 남는다. 나중에 이 vault를 팀과 공유하게 되면 그 이력까지 함께 넘어간다.

스킬이 묻는 문구는 "이 문서는 팀 공유 vault에 커밋 가능한가"다. 개인 vault에서는 "git 이력에 영구히 남겨도 되는 문서인가"로 읽는다.

고객사 자료라면 "vault 밖 변환 모드로 해줘"라고 답한다. 변환 결과만 받고 vault에는 아무것도 쓰지 않는다.

한국 기업 문서에서 특히 조심할 것 — 병합 셀 표

워드 문서의 병합된 셀이 있는 표는 아직 검증되지 않았다. 마크다운 표로 안 떨어지고 평문으로 뭉치거나, 표 개수가 tables=0으로 잘못 세어질 수 있다.

우리 문서의 표는 대개 셀이 병합돼 있다. 변환 후 표가 표로 보이는지 반드시 눈으로 확인하고, 뭉쳐 있으면 화면을 그대로 남겨 달라 — 그게 이 도구를 고칠 근거가 된다.

변환 결과가 쓸 만한지 판정하기

변환이 끝나면 스킬이 통계 한 줄을 보여준다.

stats chars=1842 tables=1 images=1 headings=3 path=D1 title=설비 점검 절차

판정은 두 축을 따로 본다.

  • 경로 품질 — path=가 D2b면 구조가 손실됐다. headings=0이 그 기계적 신호다
  • 밀도 — chars가 충분한가
charsimages판정
≥ 300무관채택 산출 그대로 쓴다
< 300≥ 1D3 제안 이미지 위주 문서다. 텍스트 추출로는 원리적으로 불가하다. 비용 고지 후 확인받는다
< 3000산출을 보여주고 사람이 판단한다. 짧은 서식·공문은 이게 정상일 수 있다
숫자만 보고 버리지 않는다

300자 기준은 초기값이다. 실측 사례로 표 하나짜리 절차서가 chars=290으로 나왔는데 변환은 정상이었다. 기준 미달이라고 폐기하지 않고 산출물을 함께 확인한다.

근거 — 실측

워드 · 2026-08-25. 한글 본문 + 4열 표(단위 ℃·±·bar, 설비코드) + 헤딩 3 + 불릿 3 + 이미지 1을 담은 docx로 두 경로를 비교했다. D1은 표·헤딩·목록·이미지·단위 기호·고유명사를 전량 보존했고, D2b는 headings=0이 나왔다.

한글 · 2026-08-21. 실문서 1건(149 KB, 표 12개)을 한글 경로와 PDF 경로로 각각 추출해 교차 검증했다. 정규화 유사도 94.7%, 수치 지문은 한글 측이 전량 일치했다. 불일치 1건은 PDF 추출의 셀 분할 아티팩트로 한글 쪽이 온전했다. 원본 1페이지 시각 대조에서 핵심 사실 16/16 일치, 병합 셀 표도 마크다운 표로 유지됐다.

먼저 말해 둘 것 — Windows는 아직 미검증이다

위 실측은 모두 macOS에서 나왔다. Windows에서는 이 도구 전체가 한 번도 돌지 않았다 — 옛 .doc 경로만이 아니라 오늘 실습이 태우는 .docx·.hwpx·PDF 경로, 한글 파일명 처리, 회귀 테스트까지 전부다. 그래서 오늘 실습이 사실상 첫 Windows 검증이 된다.

아래 4개를 관찰해 채팅에 남긴다. 실패도 오늘의 성과다.

  • path=에 무엇이 찍히는지
  • 제목·표 개수가 눈으로 센 값과 맞는지
  • 한글 파일명이나 공백이 있는 경로에서 성공하는지
  • 결과에 C:\ 같은 내 컴퓨터 경로가 남지 않는지

무엇이 어디에 생기나

변환이 끝나면 원본은 보존되고 마크다운 사본이 인박스로 간다. 원본을 옮기는 게 아니라 복사해 두는 것이라, 원래 문서함은 그대로 남는다.

설비-점검-절차.docx 를 변환한 결과
├─ raw/doc/설비-점검-절차.docx 원본 그대로 · append-only (수정·삭제 금지)
├─ raw/doc/media/설비-점검-절차/ 문서에 박혀 있던 이미지
└─ Clippings/설비-점검-절차.md 변환된 마크다운 · 다음 단계(위키화)의 입력

마크다운 맨 위에는 출처 정보가 붙는다. 원본이 어디 있고 어떤 경로로 변환했고 표·이미지가 몇 개였는지 — 나중에 이 문서를 의심할 때 되짚을 근거다.

  • D3 산출은 페이지 마커 수 = 렌더된 페이지 수
  • 모든 산출 경로가 vault 아래인지 (vault 밖 변환 모드에서는 조건이 반대)

fail-closed 설계다. 도구가 없으면 안내 후 중단하고 자동 설치하지 않는다. 변환 실패(손상·암호) 시 Clippings/·raw/를 건드리지 않는다. 모든 외부 명령에 300초 timeout이 걸려 있다 — Word COM 모달이나 LibreOffice 첫 실행 프롬프트에서 무기한 멈추면 원인을 찾기 어렵기 때문이다.

실습 — 내 문서로 직접 변환하기

18′
한 줄 워드와 한글을 전원 직접 변환한다. PDF는 poppler가 있는 사람만 하고, 없으면 화면 시연으로 본다.
어디에 입력하는가 — 이걸 먼저 맞춘다

오늘 실습은 터미널의 Claude Code에서 한다. 변환 스킬이 스크립트를 실행해야 하는데, 그게 되는 환경이 여기다.

cd ~/knowledge     # vault 폴더로 이동
claude             # Claude Code 실행

Claude Desktop 앱의 채팅창이 아니다. Desktop 앱은 폴더를 읽고 쓸 수는 있지만 오늘 쓰는 변환 스크립트를 실행하지 못한다. 프롬프트가 안 먹으면 먼저 여기부터 확인한다.

실습용 샘플

자기 문서로 해도 되고, vault에 넣어 둔 샘플로 해도 된다. 샘플은 projects/second-brain/samples/에 있다.

파일무엇을 확인하나필요한 도구
설비-점검-절차.docx 제목·표·목록·이미지가 모두 살아남는가 pandoc 있다
점검-결과-보고.hwpx 한컴오피스 없이 표까지 뽑히는가 uv 있다
안전-교육-자료.pdf 텍스트 PDF가 그대로 채택되는가 poppler 별도 설치
점검-기록지-스캔.pdf 글자가 0인 스캔 문서를 스킬이 알아채는가 poppler + Node 시연으로 본다

전부 합성 데이터다 — 설비코드·부서·측정값이 모두 가상이라 커밋해도 문제없다. samples/README.md 참조.

내 문서로 할 경우

실습 문서는 내 repo 이력에 남아도 괜찮은 것으로 고른다. 고객사 자료·개인정보가 든 문서는 쓰지 않는다.

단계

1

워드 문서 — 구조가 남는지 확인 전원

아래 두 줄을 한 메시지에 함께 붙여 보낸다.

이 워드 파일 마크다운으로 변환해서 Clippings에 넣어줘
projects/second-brain/samples/설비-점검-절차.docx

진행 중 확인 요청이 두 번 온다.

  • "이 문서는 팀 공유 vault에 커밋 가능한가" — 스킬이 쓰는 문구가 이렇다. 개인 vault에서는 "git 이력에 영구히 남겨도 되는가"로 읽는다. 샘플이면 예로 답한다
  • 통계와 전략 확인 — path=·headings·tables를 눈으로 보고 진행
2

한글 문서 — 한컴 없이 되는지 확인 전원

이 hwpx 변환해서 Clippings에 넣어줘
projects/second-brain/samples/점검-결과-보고.hwpx

한컴오피스가 없어도 표가 마크다운 표로 떨어져야 한다. 결과 MD에서 | 설비코드 |로 시작하는 표 줄이 보이는지 확인한다. 첫 실행은 필요한 라이브러리를 받아오느라 20~30초 걸린다 — 멈춘 게 아니다.

3

PDF — 판정이 갈리는 것 확인 poppler 있는 사람만

이 PDF 변환해서 Clippings에 넣어줘
projects/second-brain/samples/안전-교육-자료.pdf

텍스트가 충분해서 그대로 채택된다. poppler가 없으면 pdfinfo·pdftoppm을 못 찾겠다며 중단된다 — 그게 정상 동작이니 시연을 보면 된다.

스캔 PDF는 화면 시연으로 함께 본다. 글자가 0이라 스킬이 "이미지 위주 문서"로 판정하고, 무료 로컬 OCR을 기본으로 제안한다. 더 정확한 비전 전사는 페이지당 약 0.045 USD가 드는 선택지로 함께 제시된다. 무료 OCR은 Node 18+ 와 1회 런타임 설치(약 330 MB)가 필요해서 오늘은 각자 하지 않는다.

4

Obsidian에서 결과 확인 전원

  • Clippings/에 마크다운이 생겼는가
  • 열어서 표가 표로, 제목이 제목으로 보이는가
  • 맨 위 출처 정보의 converted_by 값이 무엇인가
  • raw/doc/·raw/hwp/에 원본이 그대로 있는가 (PDF를 했다면 raw/pdf/도)

끝나면 stats 줄을 그대로 교육 채팅에 붙인다. 완료 확인도 되고, Windows 첫 검증 데이터로도 쓴다.

이 실습의 핵심

3단계에서 스킬이 스스로 "이건 안 된다"고 말하는 것을 보는 게 요점이다. 도구가 없으면 멈추고 무엇을 깔아야 하는지 알려주며, 스캔 문서는 억지로 변환해 빈 파일을 만들지 않고 왜 안 되는지와 대안과 비용을 먼저 말한다.

이 판단을 사람이 매번 하지 않아도 되게 만든 것이 Skill이다.

여기까지가 오늘 실습이다. 위키로 만드는 단계는 §06에서 설명하고, 실제 작업은 3주차 첫 10분에 함께 한다. 오늘은 인박스에 재료를 넣는 것까지다.

막히는 경우
증상조치
스킬이 안 뜬다 — 무슨 말인지 모르겠다고 한다 Windows 심링크가 깨진 경우다. 개발자 모드 켜고 다시 clone해야 한다. 세션 중에는 해결이 어려우니 화면 시연으로 보고 세션 후 함께 고친다

재실습할 때 — raw/ 규칙의 유일한 예외

raw/는 원칙적으로 수정·삭제 금지다. 단 오늘 넣은 합성 샘플에 한해, 재실습을 위해 raw/의 해당 파일과 Clippings/의 산출 MD를 지워도 된다.

실제 업무 문서가 들어간 뒤에는 지우지 않는다. 이 예외는 교육용 샘플에만 적용된다.

변환과 위키화를 분리한 이유 — 변환은 파일 단위, 위키화는 하루 1회 배치다

인제스트(위키화)가 대신 해주는 일

클리핑 처리해줘 한 줄이면 Claude가 아래를 순서대로 수행한다. git 명령을 직접 쓸 일은 없다.

  1. 작업 브랜치를 만든다 — 원본을 건드리지 않고 별도 공간에서 작업한다
  2. 원문을 raw/로 옮긴다 — 내용은 그대로, 파일명만 정규화한다
  3. 개념을 뽑아 wiki/에 문서를 쓴다 — 한 개념당 한 파일, 템플릿을 적용한다
  4. 색인을 갱신한다 — wiki/INDEX.md·토픽 인덱스·메모리의 Last Ingest 한 줄
  5. 커밋하고 PR을 연다 — 무엇이 바뀌었는지 한 화면에서 볼 수 있다
혼자 쓰는데도 PR을 쓰는 이유

혼자 쓰는 vault라면 바로 커밋해도 될 것 같다. 그런데 PR을 한 겹 두는 이유가 둘 있다.

  • AI가 만든 결과를 눈으로 확인하는 관문이 된다. 위키 문서 5개가 한꺼번에 생겼을 때 무엇이 어떻게 쓰였는지 diff로 본다
  • 나중에 팀과 공유하게 되면 그대로 확장된다. 리뷰어만 추가하면 되고 절차를 새로 만들 필요가 없다
넘지 않는 선
  • PR을 여는 것까지는 자동, merge는 내 명시적 승인이 필요하다. AI가 위키에 직접 반영하지 않는다
  • master에 직접 push하지 않는다
  • Obsidian Git 플러그인으로 직접 push하지 않는다 — 1주차 설정대로 auto-pull만 켜져 있으면 그대로 두면 된다
  • raw/·archive/의 파일을 수정·이동·삭제하지 않는다 — 원본 보존 구역이다
개발자 심화 — 브랜치·검증 계약

작업자 slug는 gh api user --jq .login → 실패 시 git config user.name의 소문자·하이픈 slug → whoami 순으로 구한다. 같은 날 재실행하면 -2, -3 접미사가 붙는다. 개인 vault에서는 slug가 항상 같지만 날짜별 구분은 그대로 유효하다.

커밋은 두 개로 정리한다. 선택적 시작 커밋(chore: stage N clippings for ingest)과 필수 결과 커밋이다. 중간에 더 쪼개지 않는다.

배포 값은 projects/second-brain/config/team-settings.yaml 한 곳에 있다. 개인 vault라면 github.vault_repo를 내 repo로 바꾸고 github.default_reviewer는 내 계정으로 두거나 비운다.

공유 불변식(메모리 크기, - Last …: 마커 중복·길이, raw/·archive/ append-only)은 한 곳에서 기계 판정한다.

python3 projects/second-brain/config/scripts/vault_verify.py \
  --lane ingest --base "$(git merge-base HEAD master)"

exit 0이 아니면 성공으로 보고하지 않고 출력된 defect를 그대로 전달한다. 금지 명령은 git push --force, git reset --hard, git clean, rm -rf, --no-verify다.

마무리 · 3주차

1′

오늘을 네 줄로 정리한다.

  • 문서를 모으는 것과 지식으로 정리하는 것은 다른 일이다. 이 vault는 그 사이에 컴파일 단계를 넣는다.
  • 컨텍스트는 유한하다. 필요할 때만 필요한 만큼 올린다.
  • MCP는 능력을 붙이고 Skill은 절차를 붙인다. Skill은 마크다운 문서 한 장이라 절차를 아는 사람이면 쓸 수 있다.
  • 문서 변환은 원본 포맷에서 직접 뽑아야 구조가 산다. PDF 우회는 표와 제목을 먼저 버린다.
다음 시간까지
  • 실제 업무 문서 2~3건을 변환해 Clippings/에 쌓아 둔다. 3주차 첫 10분에 이걸로 위키를 만든다 — 포맷을 섞어서 넣으면 더 좋다
  • Windows에서 이상하게 동작한 것이 있으면 화면 문구를 그대로 남긴다 — 특히 병합 셀 표가 제대로 나오는지
